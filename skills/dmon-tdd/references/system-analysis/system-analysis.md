# 系分

需求已经确认之后、拆实施计划之前使用。系分是给全栈开发用的系统分析,不只是设计说明:还要写清兼容性、发布风险、用户影响和排期。

宣布 "Using dmon-tdd 系分来 [目的]",然后严格按本文执行。

## 硬门槛

- **先读已确认材料。** 打开人类搭档给出的 PRD、原型、设计稿、已定稿 spec。材料里没有的事实标成「待确认」,不要编接口、表结构、人天或负责人。
- **不写实现代码。** 系分结束前不新建功能代码、不改业务逻辑。
- **九章都要有。** 某一章确实不适用时,写「不适用」并给出理由,不要删章节标题。
- **写完停下来。** 把文档交给人类搭档确认。未确认不得进入阶段 2(计划)或阶段 3(实现)。
- **尽量简单明了。** 一句只说一件事。能用一行表或一张图说清的,不要写成大段说明。删掉背景铺垫、同义反复和「众所周知」。

## 写法

对照材料写,对照结构排版。

**引用图。** PRD、原型、设计稿里的图片,以及用户这条提示词里附带的图片,都要引用,不要只靠文字复述画面。用 markdown 图片语法,路径或链接用材料里的原地址;提示词里的图用用户给出的路径或附件标识。图下用一句话写它说明什么。看不清或没有原文件时标「待确认」,不要凭印象重画一张假图。

**用对格式。**

| 内容 | 用什么 |
|---|---|
| 字段、接口、配置、兼容结论、排期、指标 | 表格 |
| 步骤、范围、风险、检查项 | 列表 |
| 请求体、响应体、配置片段、错误码示例 | 代码块 |
| 流程、调用、模型、表关系 | 图 |

**善用图。** 图用 mermaid,嵌在对应章节里,不另附一份「图册」。按事情选图,不要为了有图而画:

| 要说清的事 | 图 |
|---|---|
| 用户操作、分支、发布步骤 | 流程图 |
| 用户、前端、后端、上下游的调用与失败分支 | 时序图 |
| 领域对象和关系 | 类图 |
| 表、字段、主外键 | ER 图 |
| 状态怎么变 | 状态图 |

一张图只讲一条路径或一组关系。节点用业务词,不写实现类名堆砌。

## 落盘

保存到 `docs/dmon/sys/YYYY-MM-DD-<topic>.md`,并纳入 git。

文首写明:

- 关联材料:PRD、原型、设计稿、spec 的路径或链接
- 状态:草稿 / 待确认 / 已确认
- 范围一句话:这次解决什么,不解决什么

## 1. 需求背景

写清业务背景、目标、适用范围,以及这次要解决的问题。单列「不在本次范围」:明确排除的页面、角色、数据、系统。关联 PRD、原型、设计稿。

## 2. 概要设计

描述整体方案和主要架构:

- 新增或修改的前端页面、组件
- 新增或修改的后端服务、接口、数据模型
- 上下游依赖和调用关系
- 数据库表、字段、索引、缓存、配置项的变更清单

没有变更的类别写「无」。

## 3. 详细设计

### 前端

页面结构、交互流程、路由、组件拆分、状态管理、权限、接口调用、异常提示。

### 后端

业务流程、领域模型、接口定义、参数校验、事务、并发控制、缓存、消息、定时任务。

### 前后端协同

接口协议、字段含义、数据格式、错误码、分页、空值处理、联调方式。字段表至少包含:名称、类型、必填、含义、空值约定。

### 系统交互

至少一张时序图或流程图,标出失败分支。有领域对象就补类图,有表结构变更就补 ER 图。

## 4. 兼容性分析

逐项回答,每项给出结论(兼容 / 不兼容 / 待确认)和依据:

1. 新代码能否读历史数据和历史配置。
2. 老代码能否读新代码写出的数据,尤其是分批发布时新旧版本共存。
3. 新前端能否调用老接口、展示历史数据。
4. 老前端能否调用新接口、忽略新增字段。
5. 接口变更是否影响其他页面、模块或调用方。
6. 库表、缓存、消息结构变更是否前后兼容。
7. 上线后是否改变其他系统或既有业务流程。

不兼容项必须写迁移或双写方案,不能只写「上线后一起切」。

## 5. 用户影响

用户能感知的变化:入口、操作步骤、展示内容、响应速度、异常提示。列出可能改变操作结果的风险,以及兜底(降级文案、旧流程入口、人工处理)。

## 6. 三板斧

发布方案围绕可灰度、可监控、可回滚。写明发布依赖、上线前准备、放量后观察什么。

- **可灰度:** Beta、业务白名单、流量比例、机房或区域、前后端开关。写清第一批是谁、怎么加大、怎么停。
- **可监控:** 前端异常、接口成功率、耗时、服务日志、业务指标、用户反馈。每个指标写观察窗口和异常阈值(未知则标待确认)。
- **可回滚:** 关入口、切回旧接口、回滚代码或配置。数据变更要写是否可逆;代码回滚后新数据怎么读。不可逆时写止损,不要假装可以回滚。

## 7. 非功能性分析

性能(首屏、交互、接口耗时、并发)、安全(权限、敏感数据)、稳定性(限流、降级、异常兜底)、可维护性。

单列联调和测试要重点验的场景:前后端联调、上下游联调、回归。每条场景写输入、期望、失败时用户看到什么。

## 8. 系统间分析

这次变更对其他系统的接口、消息、数据、权限依赖有没有变化。新增的第三方或公共组件要评估稳定性、性能、兼容性和故障降级。没有外部依赖时写「无」,并说明判断依据。

## 9. 排期

按前端、后端、联调、测试、发布拆工作量。给出里程碑、上下游依赖、负责人。为人熟悉业务、技术调研、沟通和风险处理留缓冲。估不出的数字标「待确认」,不要填看起来精确的假人天。

## 完成前检查

- [ ] 九章标题都在,不适用的写了理由
- [ ] 范围外事项已列出
- [ ] 兼容性七问都有结论
- [ ] 三板斧写了灰度步骤、监控指标、回滚动作
- [ ] 数据变更写了是否可逆
- [ ] 待确认项集中列在文末,没有被写成既定事实
- [ ] 句子短,能用表或图的地方没有写成大段
- [ ] PRD 和提示词里的图片都已引用,图下有一句话说明
- [ ] 字段、兼容结论、排期用了表格;报文和配置用了代码块
- [ ] 调用关系有时序图或流程图;有模型或表变更时有类图或 ER 图
- [ ] 已停下来等待人类搭档确认
