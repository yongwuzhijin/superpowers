# 系统化调试

## 概述

**核心原则:** 在尝试任何修复之前,永远先找到根因。症状式修复就是失败。

**违反这套流程的字面意思,就是违反调试的精神。**

## 铁律

```
没有先做根因调查,就不准修复
```

如果你还没完成第 1 阶段,你就不能提出修复方案。

## 何时使用

用于任何技术问题:
- 测试失败
- 生产环境的 bug
- 非预期行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用:**
- 有时间压力时(紧急情况让人忍不住去猜)
- "就一个快速小修复"看起来很显然时
- 你已经试过好几个修复了
- 上一个修复没起作用
- 你还没完全搞懂这个问题

**别在以下情况跳过:**
- 问题看起来很简单(简单的 bug 也有根因)
- 你很赶时间(赶只会保证返工)
- 老板要你现在就修好(系统化比瞎折腾更快)

## 四个阶段

在进入下一阶段之前,你必须完成当前阶段。

### 第 1 阶段:根因调查

**在尝试任何修复之前:**

1. **仔细读错误信息**
   - 别跳过报错或警告
   - 它们往往包含着确切的解法
   - 完整读完堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗?
   - 确切步骤是什么?
   - 每次都会发生吗?
   - 如果无法复现 → 收集更多数据,别猜

3. **检查最近的改动**
   - 什么改动可能导致了这个?
   - Git diff、最近的提交
   - 新的依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时(CI → 构建 → 签名,API → 服务 → 数据库):**

   **在提出修复之前,加上诊断埋点:**
   ```
   对每一个组件边界:
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每一层的状态

   跑一次,收集证据,看清它在哪里坏掉
   然后分析证据,定位出问题的组件
   然后再去调查那个具体的组件
   ```

   **示例(多层系统):**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示:** 哪一层坏了(secrets → workflow ✓,workflow → build ✗)

5. **追踪数据流**

   **当错误深藏在调用栈里时:**

   完整的反向追踪技术见本目录下的 `root-cause-tracing.md`。

   **速览版:**
   - 这个坏值从哪里冒出来的?
   - 是谁带着这个坏值调用了它?
   - 一路往上追,直到找到源头
   - 在源头修,而不是在症状处修

### 第 2 阶段:模式分析

**在修复之前先找到模式:**

1. **找到能工作的例子**
   - 在同一个代码库里定位类似的、能工作的代码
   - 什么东西能工作,而且和坏掉的那个很像?

2. **对照参考实现**
   - 如果是在实现某个模式,把参考实现完整读一遍
   - 别略读——每一行都读
   - 在应用之前彻底理解这个模式

3. **找出差异**
   - 能工作的和坏掉的之间有什么不同?
   - 列出每一处差异,再小也要列
   - 别想当然地觉得"那不可能有影响"

4. **理解依赖**
   - 这东西还需要哪些其他组件?
   - 需要什么设置、配置、环境?
   - 它做了哪些假设?

### 第 3 阶段:假设与检验

**科学方法:**

1. **形成单一假设**
   - 清晰地陈述:"我认为 X 是根因,因为 Y"
   - 把它写下来
   - 要具体,别含糊

2. **做最小化检验**
   - 做尽可能小的改动来检验假设
   - 一次只动一个变量
   - 别一次修好几处

3. **确认后再继续**
   - 起作用了吗?是 → 第 4 阶段
   - 没起作用?形成一个新假设
   - 别在上面继续叠加修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 别不懂装懂
   - 求助
   - 再多做点研究

### 第 4 阶段:实施

**修根因,不修症状:**

1. **创建一个失败的测试用例**
   - 尽可能简单的复现
   - 尽量做成自动化测试
   - 没有测试框架就写一次性的测试脚本
   - 修复之前必须先有它
   - 用 `../shared/test-driven-development.md` 技能来写像样的失败测试

2. **实施单一修复**
   - 针对已识别出的根因
   - 一次一处改动
   - 别搞"顺手"的改进
   - 别捆绑重构

3. **验证修复**
   - 测试现在通过了吗?
   - 没有弄坏其他测试吧?
   - 问题真的解决了吗?
   - 在宣称成功之前,用 `../5-review/verification-before-completion.md` 技能

4. **如果修复不起作用**
   - 停
   - 数一数:你已经试了几个修复了?
   - 如果 < 3:回到第 1 阶段,带着新信息重新分析
   - **如果 ≥ 3:停下来,质疑架构(见下面第 5 步)**
   - 没经过架构层面的讨论,别去尝试第 4 个修复

5. **如果 3 个以上的修复都失败了:质疑架构**

   **表明是架构问题的模式:**
   - 每个修复都在不同的地方揭示出新的共享状态/耦合/问题
   - 修复起来需要"大规模重构"
   - 每个修复都在别处制造出新症状

   **停下来,质疑根本前提:**
   - 这个模式从根本上站得住脚吗?
   - 我们是不是"纯靠惯性硬撑着用它"?
   - 我们该重构架构,还是继续修症状?

   **在尝试更多修复之前,和你的人类搭档讨论**

   这不是一个失败的假设——这是一个错误的架构。

## 危险信号 - 停,然后遵循流程

如果你发现自己在想:
- "先快速修一下,以后再调查"
- "先试着改改 X,看看行不行"
- "加上好几处改动,跑测试"
- "跳过测试,我手动验证一下"
- "多半是 X,我来修那个"
- "我没完全搞懂,但这样也许能行"
- "模式说的是 X,但我要换个方式改一改"
- "主要问题有这些:[没做调查就列出一堆修复]"
- 在追踪数据流之前就提出解决方案
- **"再试一个修复"(在已经试过 2 个以上时)**
- **每个修复都在不同的地方揭示出新问题**

**以上所有情况都意味着:停。回到第 1 阶段。**

**如果 3 个以上的修复都失败了:** 质疑架构(见第 4.5 步)

## 你的人类搭档发出的、说明你做错了的信号

**留意这些纠偏话语:**
- "那件事没发生吗?" —— 你没验证就假设了
- "它会不会显示给我们……?" —— 你本该加上证据收集
- "别猜了" —— 你在没搞懂的情况下提修复
- "好好深想一下这个" —— 质疑根本前提,别只盯着症状
- "我们卡住了?"(带着挫败感) —— 你的路子行不通

**当你看到这些时:** 停。回到第 1 阶段。

## 常见的自我合理化

| 借口 | 现实 |
|--------|------|
| "问题很简单,不需要流程" | 简单问题也有根因。流程对付简单 bug 很快。 |
| "紧急情况,没时间走流程" | 系统化调试比瞎猜瞎试的折腾更快。 |
| "先试试这个,再调查" | 第一个修复就定了调子。一开始就做对。 |
| "我确认修复能用之后再写测试" | 没测过的修复留不住。测试先行才能证明它。 |
| "一次多修几处能省时间" | 没法分辨是哪个起了作用。还会引入新 bug。 |
| "参考太长了,我改改这个模式就行" | 一知半解必然带来 bug。完整读完。 |
| "我看出问题了,让我来修" | 看到症状 ≠ 理解根因。 |
| "再试一个修复"(在 2 次以上失败之后) | 3 次以上失败 = 架构问题。质疑模式,别再修了。 |

## 速查

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、查改动、收集证据 | 搞懂是什么、为什么 |
| **2. 模式** | 找能工作的例子、对比 | 找出差异 |
| **3. 假设** | 形成理论、最小化检验 | 得到确认或新假设 |
| **4. 实施** | 创建测试、修复、验证 | bug 解决,测试通过 |

## 当流程揭示"没有根因"时

如果系统化的调查揭示问题确实是环境性的、依赖时序的,或来自外部:

1. 你已经走完了流程
2. 把你调查过的内容记录下来
3. 实施恰当的处理(重试、超时、错误信息)
4. 加上监控/日志,供将来调查

**但是:** 95% 的"没有根因"其实是调查没做完。

这些技术是系统化调试的一部分,都在本目录下:

- **`condition-based-waiting.md`** - 用条件轮询替代随意设定的超时
